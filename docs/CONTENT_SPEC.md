# Content Spec

This document defines exactly what content the portfolio needs. It does not contain the actual content — that belongs in `/content` — but specifies what must be written and what's optional.

## Personal (mandatory unless noted)

| Field | Mandatory? | Notes |
|---|---|---|
| Name | Yes | |
| Title | Yes | e.g., "Jr. Product Designer" / "UI/UX Designer" — should match target role language |
| One-line positioning | Yes | Shown in hero — what kind of designer, what you're looking for |
| Short bio (2–4 sentences) | Yes | Kept brief per `INFORMATION_ARCHITECTURE.md` — case studies carry the proof |
| Location | Optional | Include only if relevant to target roles (e.g., remote-friendly note, or city if targeting local companies) |
| Contact email | Yes | |
| LinkedIn | Yes | |
| Resume (PDF) | Yes | Must be a real, up-to-date file — this is one of the two most-requested pieces of content by recruiters |
| Photo | Optional | Recommended for warmth/trust but not required |

## Projects — general rules

- **4 total case studies.** 2 strong (Matrimonial App, Delivery Partner App), 2 lighter.
- Each project must honestly indicate its own depth — do not pad the lighter 2 to falsely resemble the strong 2.
- Every project must have, at minimum: title, one-line summary, role, timeline, problem statement, final screens, and outcome. Everything else is conditional on what's honestly available.

## Per-project content fields

| Field | Mandatory? | Notes |
|---|---|---|
| Title | Yes | |
| One-line description | Yes | Shown on project card (Home) — problem + role in one sentence |
| Role | Yes | Be specific (e.g., "Sole designer — research, UI, testing" reflecting the candidate's actual internship scope) |
| Timeline | Yes | Duration, not necessarily exact dates |
| Team | Optional | Include if relevant context (worked solo vs. with PM/eng) |
| Problem / Context | Yes | What problem, for whom, why it mattered to the business/users |
| Research | Conditional | Include only what's real — do not invent research methodology that wasn't performed |
| Insights | Conditional | Same rule — real findings only, even if brief |
| User flows | Conditional | Include if diagrams/flows still exist or can be honestly redrawn from memory (mark as reconstructed if so) |
| Wireframes | Conditional | Only if preserved; do not recreate fake "early exploration" wireframes to imply an iteration history that didn't survive |
| Visual design (final screens) | Yes | This is the strongest asset available (polished, final screens) — present at high fidelity |
| Design system / components | Conditional | Include if the internship produced reusable components/patterns worth showing |
| Prototype | Conditional — 1 project only | Only the project with a real interactive prototype gets this section |
| Outcome | Yes | What shipped; measurable impact if known, honest qualitative outcome if not (e.g., "shipped to production," "positive internal feedback") — never fabricate metrics |
| Design Decisions (reflection) | Yes, but scaled honestly | For the 2 strong projects: specific rationale per major decision. For the 2 lighter projects: a shorter, honest reflection — explicitly framed as reflection where detailed iteration history wasn't preserved |
| Learnings | Yes | Brief, personal — valuable for entry-level narrative, shows growth mindset |

## Handling the "deleted iteration history" constraint

Per the interview: iteration/version history was mostly not preserved, and reasoning can only be **partially** reconstructed. Content guidance:

- Never present reconstructed reasoning as if it were preserved documentation (no fake dates, no implied "here's my actual v1/v2/v3" if those screens don't exist).
- Acceptable framing: *"Looking back, the reasoning behind [decision] was..."* — honest, first-person reflection.
- Where reasoning truly can't be reconstructed, it's acceptable and expected to simply not address that specific decision — do not fabricate to fill a template.
- The two strong projects should aim for as much honest specificity as memory allows; the two lighter projects can lean more on the final screens + outcome, with a shorter reflection.

## Content for the "About" section

2–4 sentences maximum in the hero-level bio. Optional extended version (skills list, tools, brief journey) only if the candidate wants a slightly deeper About — kept separate from the hero so it never displaces case-study content in visual priority.

## Resume content

Standard resume content (experience, education, skills) — outside this project's scope to draft, but the file must be finalized before build, since "resume" is a MUST HAVE, always-available piece of content per the IA.

## Contact content

Minimum: email + LinkedIn. No contact form required for v1 (see IA rationale).

## Mandatory vs. optional summary

**Mandatory for launch:** personal info (except location/photo), resume, contact, all 4 projects' title/summary/role/timeline/problem/final screens/outcome/learnings, Design Decisions section for at least the 2 strong projects.

**Optional / conditional:** location, photo, research/insights/flows/wireframes (only where real), design system section, prototype section (1 project only), extended About.
